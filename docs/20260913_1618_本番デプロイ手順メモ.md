# 本番デプロイ手順メモ

## 背景

`AGENTS.md` に記載の通り、`.github/workflows/deploy.yml`（`develop`/`main` へのpushで自動起動する
「Migrate DB then Deploy」）は、このフォーク（`YuugouReLU-B/action-board`）では**Secrets/Variablesが
一つも設定されておらず機能していない**（2026-08-08以降の全実行が最初の「Link Supabase project」で失敗）。

そのため、本番反映は現状すべて手動で行う必要がある。2026-09-13時点で判明している手順を残す。

## フロントエンド（Vercel）

- Vercelプロジェクト: **`relu-branch/hamadori-quest`**（本番URL: https://hamadori-quest.vercel.app）
  - 2026-09-19時点で `yuugouohnos-projects` にこのプロジェクトは無い。scope を間違える／省略すると
    `Not authorized` で落ちる（エラーメッセージからは権限不足に見えるが、実際は別チームを見ている）
- **Gitリポジトリとの連携（Vercelの自動デプロイ）は行っていない**（`vercel.json` で `main`/`develop` 両方
  `deploymentEnabled: false` にしてあるのに整合）。デプロイは常にCLIから手動実行。
- 本番用の環境変数（`NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `BASIC_AUTH_USER/PASSWORD` 等）
  はVercel側（Production環境）に設定済み。ローカルの `.env` とは別物。

### 手順

```bash
# 初回のみ: このディレクトリをVercelプロジェクトに紐付ける
npx vercel link --yes --project hamadori-quest --scope relu-branch

# 本番デプロイ（mainの内容を出す。事前に該当ブランチ/コミットをcheckoutしておく）
npx vercel --prod --yes --scope relu-branch

# デプロイしただけでは本番URLに反映されないことがある。
# hamadori-quest.vercel.app が古いままなら昇格させる
npx vercel promote <デプロイURL> --scope relu-branch
```

- `.vercel/project.json` の `orgId` が古いチームのままだと、`--scope` を付けても失敗することがある。
  その場合は `npx vercel link` をやり直す。
- **`--prod` は「本番ターゲットのデプロイを作る」だけで、本番エイリアスへの昇格が自動とは限らない。**
  デプロイ後に `curl` で本番URLを叩き、新しいコードが出ているか必ず確認すること
  （2026-09-18のデプロイでは、`--prod` 後も `hamadori-quest.vercel.app` が旧コードを返し続け、
  `vercel promote` で初めて切り替わった。次のデプロイでは自動で昇格していたので挙動は一定しない）。

- `vercel link` を実行すると `.vercel/`（プロジェクト紐付け情報）と `.env.local`（`VERCEL_OIDC_TOKEN`）が
  生成される。どちらもgitignore対象（`.vercel` は元から、`.env.local` は既存の `.env*.local` ルールで対象）。
  **`vercel link` はなぜか `.gitignore` に `.env*` という行を追記することがある**（既存の
  「`.env*.local` に絞っている」という意図を上書きしてしまう）。実行後は `git diff .gitignore` を確認し、
  意図しない追記があれば `git checkout -- .gitignore` で戻すこと。
- 公開前はサイト全体にBasic認証をかけていた（`BASIC_AUTH_USER`/`BASIC_AUTH_PASSWORD`、Vercel側で設定）。
  2026-09-19時点では外れており、`curl` で 200 が返る。401が返る場合はBasic認証が有効なだけで、
  デプロイ自体は成功している。

### 実行リージョン

- `vercel.json` で `"regions": ["hnd1"]`（東京）を指定している。**外すとデフォルトの iad1（米バージニア）に戻る。**
- 本番Supabaseは `ap-northeast-1`（東京）なので、関数が米国だとDBとの往復ごとに150〜200ms余計にかかる。
  実測で `/`（DBを引くページ）が 1.34s → 0.27s、`/sign-in` が 1.02s → 0.17s になった（2026-09-19）。
- 実行場所はレスポンスヘッダ `x-vercel-id` の2つ目で分かる（`hnd1::hnd1::…` なら東京実行）。

## データベース（Supabase本番）

- **この環境には本番Supabaseへの認証情報（`SUPABASE_ACCESS_TOKEN` / プロジェクトref / DBパスワード）が
  存在しない。** そのため、マイグレーションの本番適用はこのセッションからは実行できなかった。
- 新しいマイグレーションを追加した場合、フロントエンドを `vercel --prod` でデプロイしても
  **本番DBには反映されない**。誰か（ユーザー本人など、本番Supabaseの認証情報を持つ人）が
  別途 `supabase link --project-ref <ref> --password <db-password>` → `supabase db push --include-all`
  を実行する必要がある。
- `posting:sync` / `season:sync` も同様に、本番へは自動反映されない。手動で本番向けの環境変数を使って
  `pnpm run posting:sync` / `pnpm run season:sync` を実行する必要がある。

## 今回（PR #30）の対応状況

- PR #30 は `develop` にマージ済み。
- `npx vercel --prod --yes` でフロントエンドは本番デプロイ済み（`https://hamadori-quest.vercel.app` に反映）。
- **`lottery_settings` テーブルのマイグレーションは本番Supabaseには未適用**。フロントエンドのコードは
  `getLotterySettings()` が失敗したら `null` を返し、呼び出し元（マイページのパネル・お知らせバナー・
  `/admin/lottery`）は `null` の場合は表示しない/エラーメッセージを出すだけなので、サイト全体がクラッシュ
  することはない。ただし機能としては、マイグレーションが本番に適用されるまで動かない。
